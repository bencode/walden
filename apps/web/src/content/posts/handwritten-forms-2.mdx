[第一篇](/posts/handwritten-forms-1)讲了识别怎样做到不悄悄地错：两个不同厂商的视觉模型各读一遍手写单据，读得一致的格直接填上，其余标黄交给人核对；投票之后，业务检查再把可疑的格标黄。读错的格只要被标黄，人核对时就会改过来，入库的数据就是对的。

这个前提守住了，人的负担却没有减轻。10 月底定稿时，每张报废单平均有六十多个黄格，而且黄格是空的：两家读法不同，程序不知道该信哪一家，就把格子留空，只在下拉里列出候选。用户在线上试用之后的反馈是「中文几乎全没填上」，等于没有替人省事。第一篇现状表里每张约 32 个黄格，是做了本篇这些调整之后的数；六十多个是 10 月底、调整之前的样子。

这一篇讲怎样在不影响正确率的前提下，减少人要动手的格。我们守着两条规则：

- 只改格里显示的值，不改格子黄不黄。黄格里先填上最可能的候选，再让模型结合主数据和历史推断一个更可能的值。填对了，人看一眼就能确认；填错了，格子仍是黄的，人照样会看到。
- 要让一个格不黄，必须有两个独立来源一致。模型推断两次得到同一个值不算，同一家模型的两份读数也不算。

例外只有一处：检验员和厂商代码两列允许小错，正确率单独统计，换来的是黄格减半。这一取舍依赖订正把这两列推得足够准，我们在后面单独讲它的依据和代价。

## 工作量看要动手的格

先说核对页怎么用。页面上方是单据照片，下方是可编辑的表格，结构和录入表单相同。人对着照片检查表格，把黄格改对，然后保存。选中一个黄格时，格子下方会列出候选：按 Enter 确认当前值并跳到下一个黄格，按 Alt 加数字直接选某个候选，直接键入就是改值。确认过的格变成浅绿。

图 1 左边是改进前：黄格多，而且都空着。当前格的两个候选是两家模型的读数，两家各错成一个形近的名字，人只能看着照片自己打字。右边是改进后：黄格少了，剩下的黄格里已经填好最可能的值，候选的第一项是模型推断的值，附一句理由。人看一眼照片，值对就按 Enter，只有个别填错的格要改。

所以黄格数并不等于工作量。一个已经填对的黄格，人只需要看一眼；一个空着或填错的黄格，人要对着照片打字。我们用「要动手的格」衡量工作量：记格 $c$ 在核对页上显示的值为 $d(c)$、真值为 $t(c)$，

$$
\text{要动手的格} = \left|\{\, c \in C \;:\; d(c) \ne t(c) \,\}\right|
$$

该有值却空着、或者本该空着却填了值，都算 $d(c) \ne t(c)$；不论格子黄不黄都计入，检验员和厂商代码两列也一并计入。黄格数另报，它对应的是人要看一眼的次数。

改进后的流程在投票和业务检查之后多了三步：订正，调用一次文字模型，为黄格推断最可能的值；填上候选，给其余空着的黄格先放一个最可能的值；收尾，给检验员、厂商代码两列定稿、不再标黄。次序如下：

```mermaid

  C --> R["订正<br/>模型推断黄格的值"]
  R --> F["填上候选<br/>其余空着的黄格"]
  F --> S["收尾<br/>容错列不再标黄"]

```

## 先在黄格里填上候选

最简单的一步不调用模型：所有空着的黄格，先填上第一个候选，格子仍标黄。

第一个候选来自投票：两家读法不同时，候选按票数排列，同票时千问的读数在前。被业务检查标黄的格，原来的值排在候选第一位，所以检查标黄之后，格里的值不变，只是变黄，候选里多出主数据给的备选，比如最接近的两个人名。

这一步不会多出静默错误：它只给已经标黄的格填值，黄格仍要人确认。对工作量的效果却很大，下一节的表里可以看到，单这一步就让要动手的格减少了一半多。

日期是例外，不取第一个候选。手写的年份常被读错，2026 读成 2016，两家又常常读得不一样。模型不知道今天的日期，也就判断不了哪个年份合理，所以日期由程序给：

```ts
// 手写年份常被读错（2026 读成 2016）：早于今天一年以上的，换成今年的同月日，晚于今天则用去年
const day = 24 * 60 * 60 * 1000

const plausibleDate = (text: string, today: string) => {
  const time = Date.parse(text)
  const now = Date.parse(today)
  if (Number.isNaN(time) || Number.isNaN(now)) return null
  if (time <= now && now - time <= 365 * day) return text
  const year = Number(today.slice(0, 4))
  const sameDay = (y: number) => `${y}${text.slice(4)}`
  const thisYear = sameDay(year)
  return Date.parse(thisYear) <= now ? thisYear : sameDay(year - 1)
}

// 日期取纠正后离今天最近的候选
const dateOf = (candidates: Candidate[], today: string) =>
  candidates
    .flatMap(item => (typeof item === 'string' ? (plausibleDate(item, today) ?? []) : []))
    .sort()
    .at(-1) ?? null
```

*节选自 `prefill.ts`。*

纠正后的日期都不晚于今天，`YYYY-MM-DD` 按字符串排序就是按日期排序，取最后一个即离今天最近的。真实日期在一年多以前的单据，会被这条规则改错，但格子仍是黄的。

## 让模型推断其余的黄格

填上候选之后，仍有大量黄格填的是错值，因为候选里常常没有正确答案。两家模型读错的方式不同：同一个手写人名，两家各错成一个形近的名字，投票只能把这两个错名字都列成候选。还有一些格是程序不敢填的：检验员的名字拆成几个字竖写在几行里，厂商代码用大括号分成几段，一个括号覆盖好几行。

人核对这些格时，用的不只是照片。这个产品平时是谁在做、从哪家厂商进货，同一张单上下几行写了什么，主数据里有没有这个名字，这些都会用上。订正这一步，就是把这些资料交给一个文字模型，让它为黄格推断最可能的值。

### 资料由程序备齐

每类单据各写一份配置，声明自己的订正方式：

```ts
export type CorrectionMaterial = {
  context: string // 交给模型的文字：主数据、历史
  accept: (field: string, value: string) => string | null // 推断值的校验，不通过返回原因
}

export type CorrectionSpec = {
  guide: string[] // 本单据的写法与推断规则
  fields: string[] // 推断哪些字段；只推断其中待核对的格
  prepare: (input: { comparison: Comparison; db: Kysely<unknown> }) => Promise<CorrectionMaterial>
}
```

通用的部分负责把单据写成文字、调用模型、筛选结果，各类单据共用；单据自己的部分只写推断规则、要推断的字段，以及怎样为这张单查资料。报废单推断操作工、检验员、报废原因、处理结果和厂商代码五列。日期由上一节的规则处理，产品和图号两家读得准，用候选。

单据写成逐行的文字。确定的格照写；要推断的黄格写成一个编号，附上两家的读数和候选；不推断的黄格只作上下文。下面是一行的样子（内容虚构，略去了几列）：

```text
第5行：产品名称=「4417钳体R」；…；报废数量=「3」；报废原因=「毛坯裂纹」；处理结果=【待定 r5.handlingResult】qwen3.8-flash读「料废」，deepseek-v4.1-flash读空；程序候选：料废；操作工=【待定 r5.operatorName】qwen3.8-flash读「何佳」，deepseek-v4.1-flash读「柯嘉」；程序候选：何佳、柯嘉；…
```

编号用 1 起的行号 `r5`，不用程序里 0 起的下标。早期的实验让模型直接写路径，它把行号当成下标，结果整体错了一行。

资料由程序为这张单并行查好，写在单据文字后面：

| 资料 | 内容 |
| --- | --- |
| 人员 | 全部人员，按操作工、班组长、检验员分三行 |
| 报废原因 | 全部原因，按工废、料废分两行，注明「不全，只是常见写法」 |
| 厂商 | 全部厂商的代码和名称 |
| 单上的产品 | 单上出现的每个产品编号在主数据里的型号、名称和货源 |
| 这些产品的历史 | 含这些编号的最近 100 张已保存的单，每个编号取 12 行 |
| 人名出现次数 | 历史里每位操作工、检验员出现的次数 |
| 原因与处理结果 | 历史里「原因 → 处理结果」的搭配，取最常见的 60 组 |

还没有已保存的单时，历史几项写成「还没有已保存的报废单」，模型只能依靠主数据，我们叫它冷启动。

系统提示告诉模型它在做什么：两个模型已各读一遍，拿不准的格标为待定，请为每个待定格推断最可能的值，最后一次提交；只推断待定格，确实应为空的填 null。后面接这类单据自己的推断规则，报废单有 9 条，下面是其中 3 条：

```text
- 厂商代码：手写的 Z 常被读成 2、3、8（207、307、807 都是 Z07）。用大括号或横线分段，每段一个代码，覆盖若干行，每行填该段代码。参考资料里该产品的货源与历史厂商。
- 没有报废数量的行（领用了但没报废），处理结果通常是 √。
- 报废原因只照这一格自己读到的字推断：两家都读成空的，填 null，不要从上下行或同一产品的其他行沿用原因（同一产品的几行通常是不同的原因）。
```

*节选，代码示例换成了虚构的代码。*

后两条是在实验中加的：一条不让模型跨行沿用原因，一条不让它给只领用、没报废的行填工废或料废。加上之后要动手的格又少了一些，见下面的表。

模型用 `deepseek-v4.1-flash`，打开思考模式（thinking），一次调用。它只有一个工具 `submit`，参数是 `{ cells: [{ cell, value, reason }] }`，每格一个值和一句理由。第一次回复没有调用 `submit` 时，提醒一次；超时设为 300 秒。

### 不给模型查询工具

最早的版本做成了 agent：给模型几个查询工具，查人员、产品、厂商、原因，让它自己决定查什么。它的问题在于查询方式。模型会一轮一轮地发几十次小查询，先查表结构、再翻页浏览整张产品表，一张单要几分钟到半个小时；推断的结果并没有更好。我们又试过只留一个批量模糊匹配的工具，并在提示里约束它的用法，模型仍会把别的行的结果挪过来，分数打平时随意选一个。

这些资料可以预先确定：人员、原因、厂商三张表都不大，产品和历史只取单上出现的编号。所以改成由程序一次查好、写进输入，模型只管推断。下表是这几种做法在同一批单据上的对照：

| 做法 | 每张要动手的格 | 每张耗时 |
| --- | --- | --- |
| 黄格留空（10 月底的线上做法） | 51.3 | — |
| 填上候选，不调用模型 | 23.9 | — |
| 模型自己调用查询工具 | 1 张单上 5–8 | 280–660 秒；更强的模型 34 分钟未提交或超时 |
| 程序备齐资料，一次调用 | 7.2 | 122 秒 |
| 再加上面两条规则 | 5.0、4.9（跑了两次） | 95–100 秒 |
| 同上，没有历史（冷启动） | 7.4 | 126 秒 |

*同一批单据在 10 月底线上的 16 次识别（11 张单，有的单拍了几张照片），真值同第一篇。实验时线上还没有多少已保存的单，历史用其他单据的真值模拟：同一周、同一批人和产品，所以有历史的几行偏乐观。*

### 不换更强的模型

推断不准时，自然会想换一个更强的模型。我们在同一批单据上比较了几个模型，用的是加两条规则之前的提示：

| 模型 | 每张要动手的格 | 平均耗时 |
| --- | --- | --- |
| deepseek-v4.1-flash | 6.3 | 115 秒 |
| qwen3.8-flash | 5.7 | 274 秒，有一张三次超时 |
| deepseek-v4-pro | 7.2 | 273 秒 |
| qwen3.8-max、glm-5.3 | 超时（420 秒） | — |

*15 张，提示为第一版。*

在这批单据上，更强的模型没有更准，只是更慢。千问 flash 要动手的格略少，但耗时是 DeepSeek 的两倍多，还有超时，所以我们用 DeepSeek。和资料是否齐全相比，模型之间的差别要小得多。

## 推断值仍然标黄

模型交回的结果先经过筛选。只采纳待定格的值：模型改了已确定的格，不会生效。再用单据自己的 `accept` 校验一遍：人名须在主数据里，检验员须是检验员，厂商代码须在厂商表里，处理结果只能是 √、工废、料废之一。报废原因不校验，因为原因是自由描述，主数据收录得不全。没通过的值记下来供评估，不显示。

通过筛选的推断值，显示在格里，并作为候选第一项，附上「推断：理由」。格子仍然是黄的。

推断值看起来很准，为什么还要人看？我们让模型对同一批单据推断了两次，按两次是否一致分开看正确率：

| 两次推断 | 正确率 |
| --- | --- |
| 相同 | 95.5% |
| 不同 | 40% |

*样本同上一节的表。*

两次一致的格仍有一部分是错的，如果据此去掉黄色，这些错就会悄悄进入台账。一个模型推断两次，用的是同样的资料和同样的推理，算不上两个来源。

推断之后剩下的错，大多落在字迹和书写习惯本身有歧义的地方：

| 列 | 典型的错 |
| --- | --- |
| 报废原因 | 草书和行话，如「毛坯大R面有气孔」推成「毛坯大面有气孔」，「缺料」推成「多料」 |
| 处理结果 | 竖写分在两行的「料废」推成工废 |
| 厂商代码 | 分段的边界，或者一整段推成另一个代码 |
| 检验员 | 单上有两位检验员时，一整段推成了另一位 |
| 操作工 | 括号覆盖几行时归错了行；相邻两行的两个人互换 |

*按格数从多到少排列，样本同上一节的表。*

## 去掉黄色要两个独立来源

订正和填上候选都只改显示的值。能把黄格变成不黄、或者直接补上一个值的，只有业务检查。第一篇讲了检查的第一种能力：把投票放过的可疑格标黄。它的第二种能力是补值或撤销黄格，条件是两个独立来源一致。

什么算独立来源？两家模型读同一张图，算两个来源，因为它们会在不同的地方犯错；同一家的两份读数、一个模型的两次推断都不算。

除了两家读数和主数据，还有一个来源是位置。位置是第三篇的内容，这里只需要知道：定位时另调一次千问，框出每处手写的位置并照录框里的字，程序据此判断这处手写落在哪一行；手写压在两行之间、主体落不到一行时，这一格标黄。代码里实际用到的组合有这几种：

| 来源一 | 来源二 | 结果 |
| --- | --- | --- |
| 位置：定位框里照录的字，主体落在这一行 | 读数：等于某家的读数，且这个值在主数据里（人名另须没有形近的人） | 撤销操作工、报废原因的黄格 |
| 两家读数：都读到，只差一个字 | 主数据：恰好其中一个在人员表里，且没有形近的人 | 操作工填主数据里那一个 |
| 两家逐格照录的散字 | 主数据：检验员名单 | 只推出一位、没有归不了属的字时，填满有内容的行 |
| 单据上的代码：两家读到的代码只有同一个 | 货源清单：这一行的产品只有这一家厂商 | 填这个厂商代码 |

另有一条结构规则不属于两个来源：只写了领用数量、产品和责任单位都空着的行是上一行的续行，照抄上一行的产品、图号、责任单位和流水号。上一行这一格是黄的，续行也标黄、候选相同，不会把不确定的值抄成确定的。

### 只有一个来源时

厂商代码是一个例子。我们试过只按历史填：一个产品在历史上一直是某家厂商，就填这家。产品换了供应商之后，整段都填错了，没有任何一格标黄。只按单据上的代码填也不行：有一张单漏读了其中一段代码。两者一致才填之后，第一篇的真值单上没有再出现这类错。

单一来源的错往往不是一格一格出现的。一个来源错了，它会把同样的错填进一整段、甚至一整列，而每一格看起来都合理。

### 照录交给模型，判断交给程序

检验员和厂商代码在纸面上很少一格一个完整的值。检验员的名字常拆成单字甚至偏旁，竖写在几行里，比如「日」「尧」两笔合起来是「晓」；厂商代码用大括号或横线分成几段，每段覆盖若干行，一张单常有两三段。

我们试过在识别提示里把这些写法讲清楚：大括号表示共用、竖写的字要合起来、代码按段输出。黄格少了一些，但这两列错得多了很多：

| 识别提示 | 检验员、厂商代码：对 / 错（格） |
| --- | --- |
| 逐格照录这一格里写的字 | 349 / 75 |
| 讲清括号、竖写、分段，按段输出 | 51 / 526 |

*第一篇的真值单，同一批读数。*

模型按段输出时，常把整段留空，或者把段的起止看错。所以现在的做法是：识别时，这两列只让模型照录每一格里写了什么；把散字归回人名、把代码分段，由程序结合主数据去做。下面是检验员的推断：

```ts
// 从两家各格照录的字推出单据上的检验员，只推出一位且没有归不了属的字时填进有内容的行，否则待核对
const inferInspector = (sheet: Sheet, rows: number[], input: RuleInput, lineKeys: string[]) => {
  const names = input.master.people.filter(person => person.role === 'inspector').map(p => p.name)
  const texts = sheetTexts(input.readings, 'inspectorName').flat()
  const hits = (name: string) =>
    texts.filter(text => [...text].some(ch => name.includes(ch))).length
  const found = names.filter(name => hits(name) >= 2).sort((a, b) => hits(b) - hits(a))
  const stray = texts.some(text =>
    [...text.replace(/[\s\-—_|/\\、,，.。]/g, '')].some(
      ch => !names.some(name => name.includes(ch)),
    ),
  )
  const single = found.length === 1 && !stray ? found[0] : undefined
  sheet.lines.forEach((_, row) => {
    const solid = lineKeys.some(key => sheet.get(row, key) !== null)
    if (!rows.includes(row)) sheet.fill(row, 'inspectorName', null)
    else if (single && solid) sheet.fill(row, 'inspectorName', single)
    else sheet.pend(row, 'inspectorName', found)
  })
}
```

*节选自报废单的检查规则 `rules.ts`。*

`hits` 数的是含有某人名字中任一字的格子数，命中两格以上才算这个人出现过。`stray` 是第一篇讲过的那条保护：有一个字归不到名单里的任何人，就可能是没认出来的另一位检验员，这时不把整列当成同一个人，交给订正去推断。厂商代码的推断类似：两家读到的代码取交集，与这一行产品的货源清单都只有同一个时才填。

## 检验员与厂商代码：接受一个错误率

这一节是全篇唯一的例外：推断值不经人看就定稿。前面说过，推断值再准也不能凭它去掉黄色，所以这里要单独交代依据和代价。

推断之后，这两列仍然大量标黄。一张单上常有两位检验员、两三段厂商代码，程序只推出一位、只对上一家的情况不多，其余的格都留给人。可这两列的黄格里，订正推断的值大多是对的，人在这里主要是看一眼、按 Enter。

我们的判断是，这两列可以放宽。这两列错了，错法有限：检验员要么空着，要么认成另一位检验员；厂商代码有货源清单可以校验。数量这类数值列不一样，错一位就直接进了统计。所以在流程的最后一步，这两列不再标黄，采用订正值，没有订正值时用填好的候选：

```ts
// 容错字段收尾：待核对的格子采用订正值（没有则保留填好的候选），不再标黄
export const settle = (spec: RecognitionSpec, comparison: Comparison, suggestions: Suggestion[]) => {
  const settled = suggestions.filter(item => tolerantAt(spec, item.path))
  const values = settled.reduce(
    (current, item) => withValue(current, item.path, item.value),
    comparison.values,
  )
  const conflicts = Object.fromEntries(
    Object.entries(comparison.conflicts).filter(([path]) => !tolerantAt(spec, path)),
  )
  return {
    comparison: { values, conflicts },
    suggestions: suggestions.filter(item => !tolerantAt(spec, item.path)),
    settled,
  }
}
```

*节选自 `settle.ts`，略去类型。*

这两列的正确率单独统计，不计入静默错误率。我们内部定的目标是：其余的列，也就是严格列，静默错误率在 0.2% 以下。

下表把这次放宽和同期的另外两项调整逐项叠加，在另一批单据上算：

| 做法 | 黄格 / 张 | 静默错误（严格列） | 检验员、厂商代码的正确率 |
| --- | --- | --- | --- |
| 当时的线上做法 | 63.1 | 9（0.14%） | 全部标黄 |
| + 位置印证、操作工两家差一字 | 58.2 | 6（0.09%） | 全部标黄 |
| + 去掉几类几乎总是对的黄格 | 53.4 | 7（0.11%） | 全部标黄 |
| + 检验员、厂商代码不标黄 | 25.4 | 7（0.11%） | 92.0% |

*69 张单：10 月底线上识别过、后来做了真值的一批（真值做法同第一篇），用当时的读数和订正值模拟。*

放宽这两列让黄格少了一半多。要说清楚省下的是什么：按本篇的口径，这两列错的格不论黄不黄都算要动手，放宽并没有减少要动手的格，减少的是人要看一眼的格。代价是这两列约 8% 的格错了，却没有人再看它们。这些错是什么样的，决定了这个代价能不能接受：

| 列 | 错的格 | 错法 |
| --- | --- | --- |
| 检验员 | 97 | 空着 30，认成另一位检验员 67 |
| 厂商代码 | 63 | 全部是分段边界错：填了本单另一段的代码 |

*同一批 69 张。*

这批单据里，两列没有出现别的错法。厂商代码没有一个不合法的值，不过，货源清单的校验拦得住不合法的代码，拦不住分段边界错：边界错了一行，填的仍是这张单上真实出现的代码。

这一取舍依赖订正。有订正值时，这两列采用的是推断的值；订正失败或超时时，只能用填好的候选定稿，而候选的准确率低得多：

| 这张单 | 张数 | 检验员、厂商代码错的格 |
| --- | --- | --- |
| 有订正值 | 63 | 3.7% |
| 订正失败或超时，没有订正值 | 6 | 51.5% |

*同一批 69 张，按线上代码重放。*

没有订正值的单，这两列有一半的格错了，而且不标黄。订正偶尔会失败，这是放宽这两列最大的风险。

表中第三行是另一次豁免：领用数量、责任单位两家读得一致时不再按数量之和标黄，两家都没读到原因时也不标黄。这几类黄格几乎总是对的，去掉它们省下的黄格不多，静默错误却多了一格。第一篇回归一节里那个被读成 200 的领用数量，就是因为这次豁免没有被标黄。

## 主数据跟着单据长

检查和订正都离不开主数据：人名检查要人员表，原因检查要原因表，厂商代码的两个来源里有一个是货源清单，订正的资料也来自这几张表。主数据缺人、缺型号，检查就会大量标黄，订正也推不准。

主数据的更新往往晚于现场：来了新人、进了新产品，不会马上有人录进去。所以保存报废单时，程序在同一个事务里补主数据。门槛是：

```text
学习(v) ⇔ v ∉ 主数据 ∧ |{ 已保存的单 d : v 出现在 d 上 }| ≥ 2
```

一个值至少在两张不同的单上出现过才加入，一次性的笔误会被挡在外面。人名按所在的列定角色，同一个名字既出现在操作工列、又出现在检验员列的不学；原因按同一行的处理结果定是工废还是料废；产品按编号、图号拼出型号；货源清单最后算，同一个产品和厂商的组合也要在两张单上出现过。

学的是人核对后保存的值，不是模型的读数，所以读错的值不会自己喂回主数据。主数据只增不删，学到的条目可以在主数据页面上核对和修改。

## 局限

推断的准确率依赖历史。没有已保存的单时，订正只能依靠主数据，要动手的格明显多于有历史时；实验里的历史是用其他单据的真值模拟的，比线上真实的历史更干净。

检验员和厂商代码的放宽依赖订正。订正偶尔会失败或超时，那张单的这两列就按候选定稿、不标黄，错得多。

订正比识别贵几倍，也慢几倍。

照片质量仍然要紧。同一张单，聊天软件转发压缩过的照片，订正之后剩下的错明显多于原图，推断救不回看不清的字。

现状的数字来自另一批单据，不是第一篇的 18 张真值单。第一篇那批单据已经作为历史保存下来，订正会从历史里读到它们自己的答案，所以没有在那批单上测现在的完整流程。

## 附录：复现要点

### 订正的模型与调用

| 项 | 值 |
| --- | --- |
| 模型 | `deepseek-v4.1-flash`，阿里云 OpenAI 兼容接口，与识别同一接口 |
| 参数 | `enable_thinking: true` |
| 工具 | 只有 `submit`：`{ cells: [{ cell, value: string \| null, reason }] }`，说明写「只调用一次」 |
| 请求次数 | 最多 2 次：第一次没调用 `submit` 时，带回模型的回复（含 `reasoning_content`），追加「请调用 submit 提交全部待定格子。」 |
| 超时 | 300 秒，不做网络错误重发 |
| 失败 | 结果只记固定文案「订正失败」「订正超时」，原因写日志；这张单照常进入核对 |

### 输入

- 单据文字：表头一行 `表头：字段=值；…`，明细每行 `第N行：字段=值；…`；
- 格的三种写法：确定的格写 `「值」` 或 `空`；要推断的黄格写 `【待定 rN.字段】模型A读「…」，模型B读「…」；程序候选：…`；不推断的黄格写 `空（不确定：…）`；
- 编号用 1 起的行号，不用 0 起的下标；
- 两家读数用原始读数，不做写法统一。

### 资料

见正文的资料表。历史取含单上编号的最近 100 张单、每个编号 12 行，只写有值的列；人名出现次数取全部历史；原因 → 处理结果取最常见的 60 组。没有历史时写「还没有已保存的报废单」。实验时整包约 1300 字。

### 提示

- system：角色（单据的核对员）、任务（为每个待定格推断最可能的值，一次提交）、约束（只推断待定格，确实为空填 null），后接单据自己的推断规则；
- 报废单 9 条规则：领用数量之和、括号与竖写覆盖的行同值、检验员拆字、厂商代码的写法与分段、处理结果的取值与毛坯类 / 加工类、没有报废数量的行为 √（第二版加）、原因照写含义与常见草书误读、原因不跨行沿用（第二版加）、人名必须在主数据；
- user：单据文字、资料、待定格清单，最后一句「资料已齐，不需要再查，直接调用 submit 提交」。

### 筛选

- 只采纳待定格；值为空不采纳；同一格只留第一条；
- 操作工须在人员表（任何角色，班组长也会顶班），检验员须是检验员，厂商代码须在厂商表，处理结果须是 √、工废、料废；报废原因不校验；
- 理由里有未转义的引号导致整段解析失败时，用正则 `"cell":\s*"([^"]+)",\s*"value":\s*(null|"[^"]*")` 逐格取值。

### 填上候选与收尾

- 顺序：检查 → 订正 → 填上候选 → 收尾，即 `settle(spec, prefill(spec, checked, today), suggestions)`；订正拿到的是检查之后、填候选之前的结果；
- 填上候选：值为空的黄格填第一个候选；日期见正文的规则；
- 收尾：单据配置里 `tolerant: true` 的字段（报废单为检验员、厂商代码）采用订正值，没有则保留填好的候选，去掉黄色；
- 核对页：非容错字段的推断值覆盖在填好的候选之上，作为候选第一项，注明「推断：理由」。

### 两个来源的规则与阈值

| 规则 | 阈值 | 依据 |
| --- | --- | --- |
| 位置印证 | 主行占比 ≥ 0.8；只放给操作工、报废原因 | 印证的黄格里操作工、原因全对，报废数量、处理结果有错 |
| 压线标黄 | 主行占比 < 0.7 | 同一批数据上定的，要在新的一批上复核 |
| 操作工两家差一字 | 编辑距离 ≤ 1，恰好一个在主数据，没有形近的人 | — |
| 检验员 | 命中 ≥ 2 格；只推出一位，且没有归不了属的字 | 第一篇的过拟合实验 |
| 厂商代码 | `^[23Z]?(\d{2})$` 写成 `Z<两位>`；两家代码的交集、货源清单都只有同一个 | 只用历史或只用单据都出现成片的错 |

### 主数据学习

- 至少在 2 张不同的已保存单上出现才加入，只增不删，记来源；
- 人名按所在列定角色，两种角色都出现的不学，签字栏不学；
- 原因按同一行的处理结果定类别，√ 的行不算，两种类别都出现的不学；
- 产品按编号、图号中段与左右件拼型号；货源清单同一组合至少 2 张单。

### 评估

- 要动手的格：核对页上显示的值与真值不同，含该有却空、本该空却填；全部列都计，黄格数另报；
- 订正实验：10 月底线上 16 次识别的读数与真值，历史用其他单据的真值模拟，模拟时排除本单；实验中填候选的日期规则与线上略有不同；
- 容错与现状：另一批 69 张单，用 10 月底线上的读数和订正值，按当时的代码重放；
- 三批样本的数不互相比较。
